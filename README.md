# Warehouse Performance Analytics: Python → SQL Server → Power BI

An end-to-end analytics project for a **fictional** 3PL beauty / FMCG warehouse ("Apex Logistic Hub"). It covers requirements gathering, synthetic data generation (Python), ETL and data cleaning (SQL Server), a star schema, and a five-page Power BI dashboard built around one north-star metric: **OTIF %**.

> **Data disclosure:** all data is synthetic and generated by the scripts in this repo. Nothing comes from a real company, client or system. The warehouse, suppliers, customers and products are invented. The patterns in the data (a late supplier, a weak pick zone, month-end slowdowns) were planted on purpose so the analysis has something to find.

---

## 1. Business Requirements

### 1.1 Business context
Apex Logistic Hub is a third-party logistics (3PL) warehouse that stores and ships beauty and FMCG products on behalf of brand clients. Because these products are batch-managed and carry expiry dates, delays or errors at any stage, from receiving through to shipping, lead to late orders, wasted stock and unreliable inventory records. Warehouse leadership currently has no single view of how each stage performs or where orders are being lost.

### 1.2 Business problem (the big question)
> **Where in the warehouse flow are we losing on-time, complete orders, and why?**

### 1.3 Objectives
1. Give leadership **one number** for order performance (OTIF %) and show which stage is dragging it down.
2. Track the four operational stages (receiving, stock, picking and shipping, inventory accuracy) against agreed targets.
3. Make every KPI **consistently defined and reconcilable** to the source data.
4. Surface near-expiry and unusable stock early.

### 1.4 Stakeholders

| Tier | Who | What they need |
|---|---|---|
| **Decision-makers** | WMS Executives (report recipients) | A one-page view of overall order performance (OTIF) and which warehouse stage is dragging it down, so they can decide where to intervene and report to clients with confidence. |
| **Internal users** | Operations management, BI team, IT, applications support | Trusted, consistently defined KPIs with stage-level detail and drill-down, so operations can fix process issues, BI can maintain the reports, and IT and applications support can trace data problems back to the source system. |
| **External / impacted** | Customers, vendors, suppliers, project teams, end-users | No direct dashboard access, but they need the outcomes it drives: orders delivered on time and complete, inbound deliveries processed promptly, and accurate stock records. |

### 1.5 Scope

| In scope | Out of scope |
|---|---|
| Receiving (inbound POs and GRNs) | Transport and last-mile delivery tracking (the project ends when the order is shipped) |
| Current stock, quality status and expiry | Billing, invoicing and client cost reporting |
| Picking and shipping (outbound orders) | Labour planning and individual staff productivity |
| Cycle counts / inventory accuracy | Real-time or streaming data (the model is a batch snapshot) |

### 1.6 Business questions → KPIs

| Stage | Question | KPI |
|---|---|---|
| Overall | Are orders leaving on time and complete? | **OTIF %** (north star) |
| Receiving | Is the stock we expect actually arriving? | Receiving Completion % |
| Current stock | How much of our stock is usable? | Available Stock % |
| Picking and shipping | Are pickers getting orders right, and how fast do orders move? | Pick Accuracy %, Order Cycle Time (hrs) |
| Inventory accuracy | Can we trust the system's stock numbers? | Inventory Accuracy % |

### 1.7 KPI definitions

| KPI | Formula | Rule that removes ambiguity | Assumed target |
|---|---|---|---|
| **OTIF %** (north star) | Orders shipped in full and on time ÷ orders due for shipment × 100 | In full = shipped qty equals ordered qty on every line. On time = ship date ≤ promised date. Cancelled orders and orders with invalid data are excluded. | 95% |
| **Receiving Completion %** | Units received ÷ units expected on PO × 100 | Cancelled PO lines excluded. | 98% |
| **Available Stock %** | Units in "Available" status ÷ total units on hand × 100 | Quarantine, damaged, expired and returns stock count as not available. Latest snapshot only. Invalid (negative) rows excluded. | 95% |
| **Pick Accuracy %** | Lines picked correctly ÷ total lines picked × 100 | Correct = right SKU and picked qty equals allocated qty. Using *allocated* qty means a stock-out is not counted as a picker's mistake. | 99.5% |
| **Order Cycle Time (hrs)** | Average of (shipped datetime − order created datetime) | Shipped orders only, with valid timestamps. | ≤ 24 hrs |
| **Inventory Accuracy %** | Count lines where counted qty = system qty ÷ completed count lines × 100 | Exact match, zero tolerance. Counts still "booked" are excluded. | 98% |

*Targets are assumptions for this synthetic exercise. In a real engagement they would be agreed with the stakeholders.*

### 1.8 Assumptions and limitations
- The data is synthetic and covers **1 Jul – 30 Sep 2026**, with the "as of" date being 30 Sep 2026.
- The stock snapshot and the transactions are generated independently, so stock on hand does not reconcile to receipts minus shipments.
- Receiving Completion dips in September. This is an artefact of the cut-off: recent POs have not been fully delivered yet when the data ends.
- The warehouse works Mon–Sat, 06:00–18:00. Orders are assumed to ship only in that window.

### 1.9 Success criteria
- All six KPIs reproduce the same value in Python (control totals), SQL and Power BI.
- Every planted data-quality issue is detected, documented and handled.
- Each dashboard page answers its business question without needing a filter to be changed first.

## 4. ETL and Data Model

### 4.1 SQL scripts (run in order)

| Script | What it does |
|---|---|
| `01_create_database.sql` | Creates `WMSDB` with `stg` and `dw` schemas |
| *(load CSVs into `stg`)* | Import Flat File wizard, every column as `nvarchar(100)` so the raw layer never rejects data |
| `02_profile_staging.sql` | Six profiling queries that confirm the planted problems exist in SQL |
| `03_build_dim_date.sql` | Date dimension (1 May – 31 Dec 2026 + Unknown row), with a month-end peak flag |
| `04_build_dimensions.sql` | Supplier, customer, location, product and quality-status dimensions, each with an Unknown row (key 0) |
| `05_build_fact_receipts.sql` | Dedupes GRNs, fixes dates and labels, aggregates receipts per PO line |
| `06_build_fact_stock.sql` | Cleans labels, buckets expiry, flags negative quantities |
| `07_build_fact_order_lines.sql` | Line-level pick accuracy flag |
| `08_build_fact_orders.sql` | Order-level flags (valid, due, on time, in full, OTIF) and cycle time |
| `09_build_fact_cycle_counts.sql` | Count-level accuracy flag and variance |

### 4.2 Star schema

**Dimensions:** `dim_date`, `dim_supplier`, `dim_customer`, `dim_location`, `dim_product`, `dim_quality_status`
**Facts:** `fact_receipts` (PO-line grain), `fact_stock` (snapshot row), `fact_order_lines` (order-line grain), `fact_orders` (order grain), `fact_cycle_counts` (count line)

Fourteen one-to-many relationships, all single-direction from dimension to fact. `fact_orders` also filters `fact_order_lines` through `order_id`, so order-level slicers (priority, order type, date) apply to pick accuracy.

## 7. Findings: so what / now what

*These findings describe patterns deliberately built into the synthetic data. They show how the analysis would be told to a non-technical audience, not real operational results.*

1. **Late and incomplete orders are mostly an "in full" problem, not a "when" problem.**
   - *What:* On-time % is 96.01% but In-full % is 92.21%.
   - *So what:* The 5.8-point OTIF gap comes mainly from orders leaving short, not leaving late.
   - *Now what:* Focus first on why lines ship short: stock-outs and pick errors.
2. **One supplier is the clear receiving outlier.**
   - *What:* Cape Botanicals delivers only 79.71% of expected units, while the other suppliers sit at about 89% or higher, and most are above 98%.
   - *So what:* Short inbound deliveries lead to stock-outs on that supplier's SKUs, which then ship short.
   - *Now what:* Raise it in a supplier performance review and consider safety stock for its SKUs.
3. **Zone C has a pick-accuracy problem.**
   - *What:* Zone C is at 97.59%, against 99.79% in Zone A and 99.72% in Zone B.
   - *So what:* Wrong or wrong-quantity picks in one zone pull the whole warehouse below target.
   - *Now what:* Review Zone C slotting, labelling and pick-path, and consider a pick-verification step there.
4. **Month-end is a bottleneck.**
   - *What:* Orders created in the last three days of a month take about 47.8 hours to ship, against 29.8 hours on other days.
   - *So what:* Peak periods push Order Cycle Time well beyond the 24-hour target and put OTIF at risk.
   - *Now what:* Plan extra capacity or shifts for month-end.
5. **Stock is usable but not clean.**
   - *What:* Available Stock is 91.53% and Inventory Accuracy is 95.81%, both below target. There is also a small but visible tail of near-expiry and expired stock.
   - *So what:* About 1 in 12 units on hand cannot be shipped, and about 1 in 24 count lines disagrees with the system.
   - *Now what:* Clear quarantine and damaged stock regularly, review near-expiry batches before they expire, and increase cycle-count coverage.

## 8. How to Run It

**Requirements:** Python 3.12 (pandas, numpy), SQL Server with SSMS, Power BI Desktop.

1. Install packages: `pip install pandas numpy`
2. Generate the data: `python 01_generate_data.py`. This creates `data/` with 11 CSVs plus `mess_log.csv` and `control_totals.csv`.
3. Check data quality: `python 02_dq_check.py`. This prints the report and saves `reports/dq_report.txt`.
4. In SSMS, run `sql/01_create_database.sql`.
5. Load each of the 11 CSVs into the `stg` schema (Tasks → Import Flat File, all columns `nvarchar(100)`, table name = file name).
6. Run `sql/02_profile_staging.sql`, then scripts `03` to `09` in order. Each script ends with a check query whose expected value is listed in `control_totals.csv`.
7. Open `powerbi/WMS_Dashboard.pbix` and point the data source to your SQL Server instance.
